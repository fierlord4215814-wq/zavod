B. УСТРАНИТЬ R3-REV-C01 И ПРОВЕРИТЬ СВЯЗАННЫЕ СОСТОЯНИЯ СВЯЗИ

Подтверждённый внешний witness: фактический frontend/src/api/client.ts после сетевого TypeError публикует «Нет связи с сервером. Действие не сохранено.». Следующий актуальный HTTP403 с корректным ответом «Нет доступа.» обрабатывается как отказ, но не снимает прежний connectivity notice. У supplied before сброс был, у R3 current он выполняется только после успешного результата. Следующий200 снимает notice. App-плашка выведена из current consumer; внешний reviewer не рендерил App. VM probe — материал для воспроизведения, не достаточная браузерная приёмка.

Воспроизведи на current клиенте, затем минимально исправь существующего owner и проверь:
- network error → актуальный403/409/404/422 → верное бизнес-сообщение без прежнего утверждения «сервера нет»;
- network error →200/204 и новая сетевая ошибка после восстановления;
- HTTP500/503, некорректный ответ/ошибка чтения body, timeout/AbortError: транспорт, доступность приложения и успех команды не смешиваются;
- late error/late success после logout, revoke, смены завода и A→B→A не меняет connectivity/данные нового контекста;
- одновременные запросы с обратным порядком завершения, отписка, закрытие слоя и retry не создают залипший или мигающий бесконечно notice;
- JSON/blob/XHR/upload consumers — проверить фактические пути и общий owner, без второго источника статуса связи;
- полученный HTTP-отказ не трактуется как успешная операция; потеря ответа после commit не доказывает, что действие не сохранено.

Нужны client-level negative/positive tests и actual App/browser witness. На отдельном реальном стенде повтори ключевой network-loss → recovery →403 путь, не только intercepted route. Не ослабляй R3 epoch/context guards и не маскируй notice CSS. HTTP-ошибка от произвольного внешнего proxy не доказывает исправность всех сервисов: границу измерения явно назови.
