## Additive replay design proposal — НИЧЕГО НЕ ПРИМЕНЯЛОСЬ

Сохранить один существующий ProcessedOperation и unique(userId,operationId). Рассмотреть nullable additive operationKind, factoryId scope, canonicalInputVersion и requestFingerprint, записываемые атомарно с результатом существующей команды. Fingerprint считается сервером по validated canonical DTO: action/target/value/unit/comment/expectedVersion семантически различаются; нормализация0/false/empty/null/undefined явно версионируется. Не включать секреты/файловые bytes и не выдумывать hash прежнего mutable результата. На replay: current actor/UFA/capability/factory/read eligibility, затем exact storedkind/fingerprint, затем current permitted result read. Другойinput409, без reexecute и без fallback на новый UUID автоматически.

Legacy NULLkind/fingerprint остаётся UNKNOWN: варианты — сохранить ограниченный readable entity replay с явным audit limitation, либо требовать conflict/manual reconcile. Выбор затрагивает lost-response UX и требует продуктового утверждения; обратный выводkind поresultKey/currentstatus запрещён. Никакой migration/application/backfill этой серией. Для нового durableконтракта нужны real transaction unique/lock, legacy/readable-ended, revoke и cross-factory отрицательные проверки.
