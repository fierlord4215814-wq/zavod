2. СНАЧАЛА УПРАВЛЯЕМЫЙ КАНАЛ, А НЕ ЦЕПОЧКА ФОТОГРАФИЙ ОТ ПОЛЬЗОВАТЕЛЯ

Пользователь уже прислал экран старого helper с запросом power-off, ответил N и сообщил о закрытии окна. VMConnect затем показывал GRUB, автозапуск и реальный install_fail.

Один раз проверь свежую identity/отсутствие старого helper и результаты SHUTDOWN000006/EXIT000007. Не запускай прежнюю очередь снова. Отказ N не записывать как успешное выключение VM. Если обнаружена реально незавершённая операция — разрешить её состояние до нового writer; если завершение уже доказано, не объявлять старый блокер вновь.

Далее выбери доступный разрешённый канал с обратной связью:
а) существующий guest SSH с проверенной identity и ключом R5, если он действительно доступен;
б) штатные разрешённые инструменты консоли/VMConnect, которые позволяют установить окно, передать ввод и получить результат.

SSH в live installer и SSH установленного /target — не одно и то же. Не угадывай пользователя, пароль или готовность сервера. Не отключай проверку host key: при неизвестном ключе сверь его с доверенным наблюдением своей VM.

Наличие нового screenshot не обязательно для каждой команды, если есть проверенные stdout/stderr/exit code и identity shell. Чтение результата команды предпочтительнее фотографирования терминала.

Если один способ захвата технически неисправен, используй другой уже разрешённый инструмент по его контракту. Если действие запрещено политикой, не обходи этот отказ сменой инструмента.

Не отправляй команды вслепую через TypeText/SendKeys, если неизвестно, куда попадёт ввод или что вернулось. Не придумывай successful capture по наличию окна. Не делай третью большую систему скриншотов.

Если ни один разрешённый способ не даёт наблюдаемый доступ, это BLOCKED_TOOL_CAPABILITY, а не «нужно согласие открыть shell». Сообщи один конкретный блокер и минимальную ручную помощь для восстановления канала, а не проси пользователя выполнять каждую последующую команду. Пока доступ не получен, выполни независимую source-диагностику и тест генератора из пункта 3.

3. КОНКРЕТНАЯ ПРОВЕРКА LATE COMMAND_3

В переданном create-seed-media.ps1 обнаружена конструкция:
@('sh','-c','install ...; printf "'+$r5Vm.vmId+'\n" > /target/etc/r5-provision-instance')

Внимание: проблема может быть не в содержимом файла, а в форме массива аргументов. Из-за приоритета comma относительно + выражение формирует элементы массива, а не обязательно одну целую строку после -c. На фотографии installer argv также показывает GUID и хвост команды отдельно от строки, заканчивающейся незакрытым printf ".

Reviewer воспроизвёл реконструированный вариант через Linux sh -n, БЕЗ исполнения install/записей: разделённая команда даёт exit2 / Unterminated quoted string; соединённая единая строка проходит синтаксическую проверку. PowerShell-генератор и Windows/guest reviewer не запускал. Это конкретное основание проверки, не уже выполненный ремонт VM.

Сначала сопоставь текущий generator, фактически приложенный seed, /autoinstall.yaml и журнал ошибки. Воспроизведи только чистое формирование late-commands на фиктивном объекте vmId — не запускай целиком генератор, создающий ключи/ISO.

Проверь длину, тип и значение каждого argv после JSON/YAML round-trip. Для sh -c весь сценарий должен быть одной строкой; дополнительные позиционные параметры допустимы только если shell-программа явно использует их корректно.

Минимальное исправление: отдельно сформированная строка/скрипт либо явно сгруппированное выражение. Проверь правильное quoting, exit semantics, синтаксис POSIX shell и ожидаемые результаты на временном фиктивном target. Parser PASS самого .ps1 недостаточен.

Не убирать command_3, не добавлять || true и не рисовать успешную receipt вместо исправления. При отсутствии /run/r5-new-disk-proof не создавать задним числом ложное доказательство «диск был пуст». Используй настоящие прежние preflight receipts или оставь конкретный пробел.

4. ВОССТАНОВИТЬ ТЕКУЩУЮ УСТАНОВКУ, НЕ СТИРАТЬ ЕЁ

Сохрани логи /var/log/installer и относящийся к сбою /var/crash, затем установи реальное состояние /target. Проверь source→argv→stderr и возможное частичное исполнение command_3.

Команды0–2 уже могли создать пользователей и sudoers. Не выполнять весь late-block повторно без проверки существующего состояния.

Предпочитай адресное восстановление: исправление невыполненной команды, проверка её результата, sudoers/SSH/пользователей, состояния пакетов, загрузчика и финальных шагов установщика. Не называй repair завершённым только потому, что записан marker-файл.

Различай installer live system и установленный корень /target; перед chroot/in-target и записью проверяй настоящий target/mount. Никаких команд разметки, mkfs, wipe или нового autoinstall на уже использованном диске.

Не нажимай Retry с прежним неисправным seed. Сначала докажи, что повторяет текущий установщик и какие действия могут выполниться заново. Если безопасного недеструктивного восстановления нет, останови только эту ветку с конкретным планом переустановки и рисками; стирание VHDX требует отдельного разрешения.

После корректного завершения разрешена штатная перезагрузка/выключение именно гостя и загрузка с его VHDX. Не использовать Reset/TurnOff/Force и не перезагружать Windows-хост. Не повторять DISM, не создавать дубликат VM/диска/switch.

Если guest shutdown integration недоступен, не запускать Stop-VM с неявным предложением жёсткого отключения. Предпочесть штатную команду внутри наблюдаемого гостя; иначе сохранить честный статус и точную причину. -Confirm:$false не является доказательством отсутствия другого prompt.

Остановка допустима при обязательном системном/tool approval, его отказе; отсутствии наблюдаемого разрешённого доступа; необходимости стереть/пересоздать VHDX; выходе за защищённые данные/системные настройки; действительно отсутствующем бизнес-решении; конфликте параллельного writer.

Не проси согласия только потому, что надо открыть Help, Enter shell, прочитать журнал, выполнить разрешённую диагностическую команду, исправить собственный seed, проверить результат или перейти к следующему уже разрешённому этапу.

Не меняй Defender/UAC/execution policy/питание/часы, не включай постоянный elevated автозапуск, не трогай рабочую PostgreSQL/service/.env/uploads/protected history. Не выполнять git reset/clean/stash/restore/rebase или несогласованный commit/push. Не запускать Cloudflare, Load/Capacity, Stage68 или физическую приёмку телефона.

Один writer, один browser worker. У диагностических команд — ограниченные timeout и фактические результаты; timeout не считать отменой побочного действия. Не оставлять старую очередь, способную неожиданно выключить гостя.

Сохраняй checkpoint после существенного этапа; это запись, а не просьба о продолжении. Не трать часы на полную переупаковку каждой мелкой операции. Один полный report/review ZIP после всей выполнимой серии либо настоящей внешней блокировки.

Обнови существующие repo-источники: это уточнение автономности, не отмена безопасности и не новый проект. Не переписывай прошлые ошибки в PASS. Library/account memory не объявлять обновлёнными без фактической записи.
