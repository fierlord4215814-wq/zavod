Это продолжение существующего MASTER R5, не R6, не новый аудит и не отдельная задача только на установку.

Разрешаю новую штатную попытку повышения прав UAC ПОСЛЕ проверки совместимости выбранного пути. Разрешение относится к включению и ограниченной настройке Hyper-V для собственной тестовой VM. Отменённую попытку Windows Sandbox автоматически не повторять.

Все исходные требования R5 к сохранности, пяти live gates, связкам модулей и финальной регрессии сохраняются. Ниже уточняется именно способ устранения блокера среды.

Дополнительного архива от пользователя не требуется.

2. КОНКРЕТНЫЙ ПУТЬ: HYPER-V + UBUNTU 24.04 LTS X64

Выбранный для проверки и реализации путь:
— Windows остаётся хостом;
— одна собственная Linux VM на Hyper-V;
— гостевая ОС Ubuntu Server 24.04 LTS x64;
— Node, PostgreSQL, backend, frontend, Playwright и браузеры запускаются внутри Linux.

Не использовать Windows Sandbox с Windows 10 для этого полного стека. Не понижать Playwright и не менять версии продукта ради поддержки Windows 10.

Не устанавливать одновременно Docker Desktop, WSL, VirtualBox и другие запасные механизмы.

До новой системной записи:
— подтвердить актуальную редакцию Windows и требования Hyper-V, включая DEP/виртуализацию;
— проверить текущие свободные RAM и диск;
— проверить совместимость текущих версий Node/PostgreSQL/Prisma/Playwright с выбранной Ubuntu;
— проверить способ автоматической подготовки гостя, передачи чистых исходников и возврата результатов;
— использовать официальные документы и проверяемые официальные образы.

Не считать совместимость хоста доказательством работоспособности всего гостевого стека.

Сохранённый inventory: 16 GiB RAM и около 39 GiB свободного диска. Эти цифры перепроверить. Составить практический бюджет: образ, гостевой диск, зависимости, браузеры, БД и evidence.

Ориентир для начала — одна VM, 2 виртуальных CPU и 4 GiB RAM; увеличение только по фактической необходимости и доступным ресурсам. Не отдавать гостю всю память.

Динамический виртуальный диск не означает бесконечное свободное место. Сохранять запас на системном диске, контролировать рост. Не удалять пользовательские файлы, старые evidence или приложения ради места. При реальном недостатке сообщить конкретно, сколько не хватает.

До включения среды выбрать осуществимый способ управления Linux-гостем и экспорта. Не предполагать, что Windows-ориентированный PowerShell Direct автоматически работает с Ubuntu.

Не превращать этот выбор в новый бесконечный обзор гипервизоров. Если выбранный путь проходит проверки — реализовать его.


3. UAC И ПЕРЕЗАГРУЗКА

Непосредственно перед UAC коротко сообщи, что будет включено и какое окно нужно подтвердить.

Используй штатное повышение прав, видимый installer и проверку фактического administrator token. Не запускать весь Codex с постоянно повышенными правами, если достаточно отдельного ограниченного helper.

Разрешены необходимые действия выбранного Hyper-V пути в границах R5. Старое отклонение UAC не считать разрешением обходить защиту.

Для новой попытки сохранить:
— exact command и script hash;
— состояние компонентов до изменения;
— результат повышения;
— actual changed features;
— terminal result;
— фактическую необходимость reboot.

Включение компонента — без автоматической перезагрузки, с NoRestart или эквивалентом.

Если система действительно потребует reboot:
— сохранить текущую точку и полную команду продолжения;
— остановиться перед перезагрузкой;
— не добавлять скрытые задачи автозапуска;
— после сообщения пользователя о ручной перезагрузке продолжить ТОТ ЖЕ R5.

Если UAC снова отменён, не повторять его циклом и не пробовать другой installer как обход. Сохранить точную ошибку.

Если reboot не требуется и среда готова — продолжать дальше без отдельного «продолжай».

Windows не обновлять/не переустанавливать. BIOS, Defender, UAC, VPN, корпоративные политики, питание и системные часы не менять. Покупки и платные подписки не разрешены.


4. РЕАЛЬНАЯ, НО ПРАКТИЧЕСКАЯ ИЗОЛЯЦИЯ

Доверенный host coordinator может читать текущие исходники проекта, готовить очищенный пакет и получать результаты.

Проверяемые guest backend/test-процессы НЕ должны получать:
— рабочий .env и credentials;
— рабочие uploads или дампы;
— подключение к рабочей PostgreSQL;
— mounts пользовательского профиля или всего репозитория;
— доступ к host/LAN/интернету во время продуктовых тестов;
— права управления хостовым гипервизором.

Разделить фазы:
а) установка гостя и получение официальных зависимостей;
б) передача чистого исходного пакета;
в) закрытая фаза исполнения тестов;
г) экспорт результатов после остановки проверяемых процессов.

Во время подготовки разрешён необходимый контролируемый доступ к официальным источникам. Это не разрешение оставить интернет и host/LAN доступными при запуске приложения.

Все компоненты приложения и Playwright могут работать в одной VM через её localhost. Для этих проверок браузер на Windows-хосте не нужен.

Выбери наиболее простой проверяемый способ передачи результатов. Реальный round-trip небольшого контрольного файла проверить до длинного тестового запуска.

При проверке изоляции использовать собственные canary-файлы и тестовые адреса, а не попытки прочитать рабочие секреты или подключиться к рабочей БД.

До backend bootstrap подтвердить:
— actual VM identity;
— собственный диск и пути;
— сетевые ограничения;
— отсутствие рабочих mounts/credentials;
— product/config/schema identity;
— отказ запуска при неправильном target или неподтверждённой изоляции.

Не подставлять manifest вместо фактического наблюдения.

Приложение и браузер не запускать под root с отключённой защитой просто ради первого зелёного результата. Привилегированную подготовку среды отделить от обычного исполнения.

Существующую рабочую PostgreSQL и её службу не читать, не копировать, не запускать, не останавливать и не изменять.
