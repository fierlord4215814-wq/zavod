2. ВЫБРАТЬ И ПОДГОТОВИТЬ ДОСТУПНУЮ ИЗОЛИРОВАННУЮ СРЕДУ

2.1. Проверка фактических возможностей

Адресно проверь:
— редакцию и сборку Windows;
— доступность аппаратной виртуализации;
— установленные компоненты/гипервизоры;
— свободную память и диск;
— совместимость с необходимыми Node/PostgreSQL/Playwright;
— возможность сохранить результаты наружу без доступа к рабочим данным.

Не предполагай заранее Windows Pro/Home, установленный Docker или доступный Hyper-V.

Перед установкой сверяй команды, системные требования и лицензирование с актуальной официальной документацией производителя. Не используй сторонние сборки, случайные PowerShell one-liners или скрипты «исправить всё».

Допустимые варианты:
— собственная виртуальная машина;
— Windows Sandbox при подходящей системе и организованном экспорте результатов;
— контейнерный стек с доказанной файловой и сетевой изоляцией.

Выбирай вариант с наименьшим необходимым вмешательством, который реально позволяет выполнить весь стек и сохранить результаты.

Не считать другое имя БД, новый порт, пустой .env или отдельный процесс под той же учётной записью достаточным доказательством технической изоляции.

2.2. Новая практическая граница изоляции

Изолировать нужно проверяемые backend/DB/frontend/test-процессы и их зависимости. Управляющий установщик/экспортёр может работать на хосте как явно ограниченный доверенный инструмент.

Не требуй невозможного «сам Codex должен перестать видеть свой репозиторий».

Подготовь отдельную очищенную копию нужных исходников, конфигурации и тестов:
— без .env;
— без uploads;
— без .git;
— без credentials;
— без рабочих дампов и защищённых исторических снимков;
— без ссылок/reparse points на рабочие каталоги.

Продуктовые исходники продолжай исправлять адресно в current repo. В стенд передавай только проверенную собственную сборку/копию с identity. Не монтируй всю рабочую папку внутрь исполняющегося тестового стека.

При необходимости предварительно получить установщики, образы, зависимости и браузеры используй отдельную подготовительную фазу с официальными источниками и фиксированными версиями.

Во время исполнения тестов:
— продуктовые процессы не имеют маршрута к рабочим сервисам, LAN и интернету;
— работают только необходимые внутренние соединения тестового стека;
— реальные SMTP/SMS/push-провайдеры выключены;
— рабочие каталоги недоступны;
— управляющие sockets/привилегии контейнерного движка не передаются backend или test runner.

Предпочитай запуск Playwright внутри того же изолированного контура: браузеру не обязательно работать на Windows-хосте.

Если используется Windows Sandbox, предусмотрите экспорт результатов до её закрытия. Передавать наружу можно только отдельный каталог результатов, а не предоставлять доступ ко всему Documents/профилю пользователя.

Если используется Docker:
— не использовать host network, privileged mode и mount Docker socket;
— не полагаться на default network как на запрет исходящего доступа;
— явно проверить доступность только разрешённых внутренних адресов;
— не публиковать порты на все интерфейсы.
При необходимости хостового доступа — только явно ограниченный loopback, без доступа из интернета.
