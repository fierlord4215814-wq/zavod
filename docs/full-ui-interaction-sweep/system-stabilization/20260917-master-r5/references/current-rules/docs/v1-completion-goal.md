# Завод v1.0 — цель завершения проекта

Этот документ фиксирует MASTER GOAL проекта «Завод» на этапе завершения v1.0. Его нужно читать перед крупными stage, аудитами, UX-проходами и архитектурными решениями. Короткие обязательные правила находятся в корневом `AGENTS.md`; этот документ объясняет цель, границы и критерии остановки разработки.

## Северная звезда

«Завод» должен стать handover-ready/self-service v1.0: mobile-first PWA/MES для завода, где основные рабочие процессы стабильны, связаны между собой и понятны обычному пользователю без участия разработчика.

Целевой пользователь — не инженер разработки. Это мастер смены, рабочий, ОКК, склад, КИПиА, холодильная служба, руководитель и администратор завода. Интерфейс должен помогать им выполнять работу, а не выглядеть как dev/demo панель.

К финалу v1.0 система должна позволять:

- выбрать завод и работать в его контексте;
- вести текущую смену;
- планировать следующую смену;
- назначать людей на линии, мойку и рабочие зоны;
- видеть прошлые смены как архив;
- создавать и вести заявки;
- фиксировать простои и связывать их с заявками;
- вести чек-листы от библиотеки до архива результатов;
- работать с объявлениями и подтверждением ознакомления;
- общаться во внутреннем мессенджере;
- вести ОКК, возвраты, некондицию, заказы/остатки, мойку, оттайку и пересменку;
- открывать архив и связанные источники;
- администрировать заводы, линии, отделы, пользователей, настройки и права без кода.

## Feature freeze

Проект находится в режиме завершения. Это означает: не добавлять новые бизнес-функции, модули, интеграции и большие архитектурные пласты без прямого запроса пользователя.

Разрешённая работа:

- исправление подтверждённых багов;
- закрытие незавершённых сценариев уже существующих модулей;
- UX-блокеры, мешающие ручному pilot;
- RBAC/security gaps;
- factory scope и cross-factory correctness;
- очистка runtime UI от Stage/test/demo/regression шума без физического удаления истории;
- связность существующих модулей;
- mobile-first polish;
- документация handover/pilot/runbook;
- targeted regressions, browser E2E, builds и scans.

Запрещённая работа без отдельного явного stage:

- новый бизнес-модуль;
- ERP/1С;
- цены, партии, себестоимость;
- backup/restore и установка;
- custom roles/job titles architecture, если это не отдельный этап;
- offline binary sync;
- внешний realtime/chat сервис;
- BI/сложная аналитика сверх уже согласованных экранов;
- физическое удаление истории;
- DB reset;
- destructive migration;
- миграции «на всякий случай».

Stage68, backup/restore, установка, эксплуатационный installer и новые крупные бизнес-функции сознательно отложены. Не начинать их в рамках режима завершения v1.0.

## Что уже построено

К моменту режима завершения уже существуют основные контуры:

- смены, текущая смена, следующая смена, будущие смены и прошлые смены;
- люди, назначения, explicit assignment board, line/work area/wash assignments;
- линии, состояния линий, текущие задания линий, простои и события;
- заявки, взятие в работу, передача, история, связь с простоями;
- архив по ключевым сущностям и открытие источников;
- чек-листы: typed rows, guided run, библиотека, назначение, периодичность, архив результатов;
- вложения, preview, guarded download/view, camera/mobile UX;
- внутренние чаты как messenger-like контур;
- объявления как fullscreen reading + per-user acknowledgement;
- ОКК, возвраты, некондиция, заказы/остатки;
- мойка, контроль мойки, вложения и оценка;
- календарь оттайки;
- пересменка;
- уведомления;
- audit;
- админка, заводы, отделы, пользователи, линии, позиции, шаблоны состава, рабочие зоны, настройки и права;
- regression scripts и Playwright coverage по историческим stage.

Нельзя создавать параллельный модуль вместо уже существующего контура. Нужно сначала найти текущую модель, API, UI, guards, tests и только потом делать минимальное исправление корневой причины.

## Критерии готовой v1.0

Система считается готовой к «Завод v1.0 — Pilot Ready», когда:

- обычный пользователь может пройти ключевые рабочие сценарии без объяснений разработчика;
- на телефоне 360-390 px основные flows не ломаются;
- desktop не имеет raw error, horizontal overflow и критичных layout gaps;
- пользовательский UI на русском;
- нет raw ids, camelCase, English placeholders, permission codes как основного текста;
- `storagePath`, `passwordHash`, tokens и secrets не уходят в API/UI/отчёты/файлы;
- backend guards являются источником истины;
- factory scope соблюдён через factoryId, UserFactoryAccess, RBAC, blocked и cross-factory denial;
- blocked/deleted users получают отказ, а не «пустую успешную выдачу» там, где должен быть запрет;
- Stage/test/demo/regression данные не засоряют ordinary runtime UI;
- archive/diagnostics сохраняют историю по правам;
- действия дают понятный feedback;
- модалки закрываются после успеха;
- submit disabled while saving;
- ошибки русские и объясняют причину;
- browser prompt/alert/confirm не используются;
- dangerous actions идут через safe app modal;
- audit пишется для важных действий;
- targeted regressions, browser E2E, affected gates, builds, Prisma checks и scans зелёные;
- зелёные тесты подтверждены реальным desktop/mobile UI-проходом для затронутых flows.

## Связность модулей

v1.0 должна ощущаться как единый рабочий инструмент, а не набор экранов.

Связи, которые нельзя ломать:

- текущая смена показывает то, что происходит сейчас;
- следующая смена показывает план, людей «Я буду», planned lines и future assignments;
- будущие назначения не влияют на текущие counters и busy state;
- прошлые смены read-only и ведут в архив/источники;
- линии связаны с заданиями, простоями, заявками, мойкой и архивом;
- простой может породить связанную заявку;
- заявка имеет историю, исполнителя, передачу, вложения и архив;
- уведомление открывает связанный объект без обхода guards;
- чек-лист идёт от шаблона к назначению, взятию в работу, guided run и архиву результатов;
- объявление читается fullscreen, подтверждается per-user и попадает в личный архив;
- руководитель видит журнал ознакомления только по правам;
- чат показывает только доступные пользователю чаты и guarded attachments;
- админка всегда работает в выбранном factory context.

Если UI скрывает кнопку, backend всё равно должен запрещать неразрешённое действие. Frontend visibility — удобство, не безопасность.

## Обязательные end-to-end сценарии

Перед завершением крупного stage проверять затронутые сценарии из этого списка:

1. ADMIN выбирает завод, видит factory context, пользователей с доступом, отделы, global services, линии, позиции, шаблоны состава, рабочие зоны, настройки и audit.
2. MASTER открывает «Смена», видит текущую, следующую, будущие и прошлые смены.
3. MASTER назначает конкретного сотрудника в конкретный слот текущей смены.
4. MASTER планирует следующую смену: видит «Я буду», planned line и future slot assignment.
5. WORKER/CONTRACTOR не получает controls мастера и не может назначать людей через backend.
6. MASTER фиксирует простой, создаёт связанную заявку и видит связь в линии/архиве.
7. TECH берёт адресованную заявку, комментирует, прикрепляет файл и закрывает/передаёт по правилам.
8. OKK создаёт запись, поля не сбрасываются, вложения видны и guarded.
9. STORE ведёт возвраты/остатки с корректными единицами и русскими ошибками.
10. Пользователь проходит чек-лист на телефоне по одному пункту, с required comment/photo/number validation.
11. Руководитель открывает архив чек-листа по шаблону как таблицу/карточки результатов.
12. Пользователь открывает чат, видит messenger-like список, сообщения, вложения и unread state.
13. Руководитель создаёт групповой чат, участник видит его, неучастник закрытый чат не видит.
14. Пользователь открывает объявление fullscreen, нажимает «Ознакомлен», оно уходит в личный архив.
15. Руководитель видит отчёт «Ознакомились / Не ознакомились», обычный сотрудник не видит чужой отчёт.
16. Пользователь открывает прошлую смену и видит read-only overview: люди, линии, простои, заявки, мойка, пересменка.
17. Mobile 360-390 px: bottom nav не перекрывает sticky actions, нет horizontal overflow, длинные названия переносятся.

## Приоритеты критичности

P0 — блокирует pilot или нарушает безопасность:

- bypass backend guards;
- cross-factory data leak;
- storagePath/secrets/passwordHash/tokens в API/UI;
- destructive action без явного разрешения;
- DB reset/physical delete;
- blocked/deleted user получает доступ;
- login/factory selection не работает;
- mobile key flow полностью непроходим.

P1 — мешает реальной работе:

- действие не выполняется или не обновляет UI;
- модалка не закрывается после успеха;
- форма сбрасывает введённые поля;
- assignment/current/future shift state смешиваются;
- Stage/test мусор в runtime;
- русский пользователь видит raw ids/permission codes/camelCase;
- archive/source link обходит guards;
- attachment недоступен молча или показывает broken image.

P2 — заметный UX debt:

- экран выглядит как dev/demo tool;
- слишком плотные строки;
- неочевидный primary action;
- слабая visual hierarchy;
- неудобные sticky actions;
- длинные таблицы без mobile layout;
- недостаточный feedback/toast.

P3 — future polish:

- richer analytics;
- exports/PDF;
- realtime WebSocket;
- reactions/reply threads;
- advanced role/job title constructor;
- import from Excel;
- conditional checklist branching;
- notification escalation.

## Правила исправлений

Перед изменениями:

1. Сделать discovery существующей модели, API, UI, guards и тестов.
2. Определить, нужна ли migration. По умолчанию migration не нужна.
3. Если migration нужна, она должна быть safe additive и обоснованной.
4. Назвать существующие контуры, которые переиспользуются.
5. Назвать, что точно не трогается.

Во время исправлений:

- исправлять корневую причину, а не маскировать симптом фильтром;
- не делать второй модуль;
- не расширять права frontend-only;
- не скрывать реальные production-like данные агрессивно;
- Stage/test/demo/regression noise скрывать из ordinary runtime, но сохранять историю в archive/diagnostics по правам;
- не использовать browser prompt/alert/confirm;
- dangerous actions только через safe modal;
- user-facing copy только на русском;
- technical ids только в advanced/diagnostic context, если это действительно нужно.

После исправлений:

- targeted regression stage;
- browser E2E stage;
- affected previous gates;
- backend build;
- frontend build;
- Prisma validate/generate/migrate status;
- seed syntax check;
- prompt/alert/confirm scan;
- mojibake scan;
- visible-English scan;
- storagePath/secrets/tokens/passwordHash scan или regression coverage;
- mobile 360-390 px UI check для затронутых flows.

## Правила тестов

Не обновлять тест только ради зелёного результата. Если старый E2E устарел из-за нового правильного UX, это compatibility update, и в отчёте нужно объяснить:

- какой UX изменился;
- почему старое ожидание стало неверным;
- какой пользовательский сценарий теперь проверяет тест;
- почему это не скрытие бага.

Regression должен проверять backend source of truth:

- RBAC;
- factory scope;
- blocked/cross-factory denied;
- audit;
- no secrets/storagePath;
- idempotency where needed;
- compatibility legacy flows.

Browser E2E должен проверять human UX:

- основной flow виден обычному пользователю;
- нет raw ids/camelCase/English placeholders;
- нет mojibake;
- нет prompt/alert/confirm;
- mobile no overflow;
- sticky actions доступны;
- действие даёт feedback.

## Условия остановки разработки

Работу по v1.0 нужно останавливать, когда:

- ключевые E2E сценарии проходят на desktop и mobile;
- P0/P1 issues закрыты;
- оставшиеся P2/P3 описаны как future и не мешают pilot;
- админка позволяет обслуживать основные настройки без кода;
- handover/runbook/pilot docs достаточно понятны;
- пользователь может провести ручной pilot без разработчика рядом;
- дальнейшие запросы уже относятся к отдельным новым этапам, а не к завершению v1.0.

Не продолжать бесконечно polish, если система достигла «Pilot Ready» и остатки являются future recommendations.

## Что сознательно не добавляем в v1.0

- ERP/1С интеграция;
- цены, себестоимость, партии;
- внешний realtime/chat сервис как обязательное требование;
- сложный BI-dashboard;
- PDF/export reports, если не запрошено отдельно;
- Excel import checklist templates;
- advanced conditional checklist branching;
- voice messages;
- advanced moderation;
- backup/restore/installer/production deployment automation;
- Stage68;
- custom role/job title architecture, если это требует отдельной модели.

## Stage68 отложен

Stage68 и любые темы backup/restore, установки, production deployment, installer, self-hosting packaging и эксплуатационной инфраструктуры отложены. Не начинать их в режиме завершения v1.0 без прямого запроса пользователя.

Если запрос пользователя тянет на Stage68 или новый большой этап, нужно прямо написать это в discovery и не запихивать работу в текущий stage.

## Финальный статус

Конечная цель текущего режима: «Завод v1.0 — Pilot Ready».

Это означает не «все возможные функции добавлены», а «существующие основные рабочие процессы связаны, защищены, понятны, проверены и готовы к ручному pilot/handover».
