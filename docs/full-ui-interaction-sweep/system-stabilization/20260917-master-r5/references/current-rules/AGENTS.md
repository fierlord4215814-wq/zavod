# Проект «Завод» — инструкции Codex

## Завод v1.0 — режим завершения

- Проект «Завод» перешёл в режим завершения v1.0.
- Не придумывать новые функции, модули и интеграции без прямого запроса пользователя.
- Перед крупным этапом и аудитом обязательно читать [docs/v1-completion-goal.md](docs/v1-completion-goal.md).
- Сначала discovery существующего контура, затем минимальное исправление корневой причины.
- Не создавать параллельный модуль, если уже есть существующий.
- Backend guards являются источником истины.
- Обязательны factory scope, UserFactoryAccess, RBAC, blocked и cross-factory denial.
- Основной интерфейс mobile-first 360-390 px; desktop также не должен ломаться.
- Весь пользовательский UI на русском, без raw id, camelCase, английских placeholders и технических кодов как основного текста.
- Не допускать storagePath, passwordHash, tokens и secrets в API, UI, отчёты и файлы.
- Запрещены DB reset, destructive migration, physical delete и очистка истории.
- Использовать safe additive migration только при доказанной необходимости.
- Не использовать browser prompt, alert и confirm.
- Stage/test/demo/regression данные не должны попадать в обычный runtime.
- Зелёные тесты не являются достаточным доказательством готовности без проверки реального desktop/mobile UI.
- Исправлять только подтверждённые баги, незавершённые сценарии, UX-блокеры, RBAC/security, качество данных и связи существующих модулей.
- Не начинать Stage68, backup/restore, установку и новые бизнес-функции.
- Для изменений обязательны targeted regressions, browser E2E, связанные gates, builds, Prisma checks и security/UI scans.
- Не обновлять тест только ради зелёного результата; compatibility update должен быть обоснован.
- Конечный статус: «Завод v1.0 — Pilot Ready».

## Локальные серверы, порты и проверки

В рамках Goal «Завод v1.0 — Pilot Ready» Codex не должен каждый раз спрашивать разрешение на обычные безопасные действия, необходимые для проверки проекта.

Разрешено без отдельного вопроса пользователя:

- проверять занятые порты 3000 и 5173;
- запускать backend dev/server process для проверки на [http://127.0.0.1:3000](http://127.0.0.1:3000/);
- запускать frontend dev/Vite process для проверки на [http://127.0.0.1:5173](http://127.0.0.1:5173/);
- выполнять health-check backend;
- перезапускать backend/frontend, если текущий процесс явно старый, зависший или мешает проверке;
- останавливать только те процессы, которые были запущены Codex в текущем блоке;
- останавливать чужой процесс только если он точно слушает порт 3000 или 5173 и мешает проверке проекта;
- повторять regression/E2E после ECONNREFUSED, если причина — backend/frontend ещё не поднят;
- использовать свежий backend/frontend для browser E2E, live UI evidence и targeted smoke.

Правила безопасности:

- не трогать другие порты без причины;
- не делать taskkill по имени node.exe вслепую;
- не убивать все Node-процессы подряд;
- перед остановкой процесса определить PID и порт;
- если PID не относится к портам 3000/5173 или невозможно доказать, что это процесс проекта «Завод», остановиться и спросить пользователя;
- не запускать seed, reset, destructive migration, cleanup данных или Stage68 под видом “поднять сервер”;
- после блока остановить временно поднятые процессы, если они больше не нужны;
- в отчёте указывать, какие процессы запускались, PID, порты и были ли они остановлены.

Не спрашивать пользователя фразами вроде:

- “можно поднять backend?”;
- “можно запустить frontend?”;
- “можно проверить порт?”;
- “можно повторить тест после ECONNREFUSED?”.

Спрашивать пользователя только если:

- нужен нестандартный порт;
- нужно остановить процесс, который не доказан как backend/frontend проекта;
- требуется seed/reset/migration apply;
- требуется изменить БД или реальные данные;
- команда выходит за обычные проверки Goal.

## Эскалация модели

- По умолчанию работать на GPT-5.5 со средним уровнем рассуждения.
- Не просить более сильную модель для обычных UI-исправлений, русификации, сборок, тестов и понятных локальных багов.
- Перед продолжением остановиться и запросить переключение на высокий уровень рассуждения, если выполняется хотя бы одно условие:
  - найден возможный обход RBAC, factory scope или доступ к чужим данным;
  - существует риск потери или неправильного изменения данных;
  - требуется сложная миграция или изменение связей существующей схемы;
  - ошибка касается расчёта смен, времени, пересекающихся интервалов или двойного учёта;
  - обнаружено архитектурное противоречие между несколькими существующими модулями;
  - два последовательных обоснованных исправления не устранили одну проблему;
  - правильность решения нельзя уверенно доказать на текущем уровне рассуждения;
  - найден P0, требующий изменения архитектурного принципа.

При эскалации:

1. Не продолжать рискованное изменение.
2. Не менять модель самостоятельно и не имитировать переключение.
3. Вернуть сообщение:
   - какая проблема найдена;
   - почему среднего уровня недостаточно;
   - какие файлы и данные затронуты;
   - что уже проверено;
   - какую модель/глубину включить;
   - можно ли после решения вернуться на средний уровень.
4. Дождаться пользователя.

Рекомендуемый текст:

«Остановился перед сложным блоком. Для него рекомендую переключить GPT-5.5 со среднего уровня на высокий, потому что: <причина>. Изменения с повышенным риском ещё не выполнял. После переключения продолжу с текущей точки».

Очень высокий уровень запрашивать только если высокий уровень уже использован и проблема остаётся доказанно неразрешённой либо затрагивает несколько архитектурных контуров одновременно.
