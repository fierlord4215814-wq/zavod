# Stage67 — Операционные потери и центр контроля руководителя

## Что закрывает этап

Stage67 добавляет управленческую операционную аналитику в существующий контур `OpsModule`, без второго модуля аналитики и без новой схемы хранения простоев/заявок.

Цель — показать руководителю не “красивые графики”, а рабочую картину:

- где теряется время на линиях;
- какие простои открыты или повторяются;
- какие заявки долго берутся в работу или закрываются;
- какие отделы получают нагрузку;
- где есть проблемы качества данных;
- какой накопительный эффект даёт сокращение мелких задержек на 10 минут в день.

## Discovery result

Переиспользованы существующие источники:

- `LineEvent` для интервалов простоя;
- `Task`, `TaskHistory`, `TaskDepartmentRecipient`, `TaskAssignee` для реакции и решения заявок;
- `LineShiftResult` для связи с выполнением текущего задания линии;
- `AuditLog` для фиксации просмотра управленческой аналитики;
- текущий экран `Статистика / Аудит` для UI.

Миграция не нужна: все данные для Stage67 уже есть в существующей модели. Финансовые потери не считаются, потому что в системе нет достоверной стоимости минуты простоя.

## Backend endpoints

Новые endpoints находятся в существующем `OpsController`:

- `GET /ops/operations/overview`;
- `GET /ops/operations/lines`;
- `GET /ops/operations/downtimes`;
- `GET /ops/operations/tasks`;
- `GET /ops/operations/departments`;
- `GET /ops/operations/repeated-problems`.

Все endpoints используют backend guards и factory scope. Рабочие роли без управленческих прав не получают доступ.

## Метрики простоев

Простой считается по событиям `LineEvent` со статусами `PAUSE` и `STOP`.

Правила расчёта:

- интервалы обрезаются границами выбранного периода;
- открытый простой считается до текущего времени и помечается как открытый;
- пересекающиеся интервалы по одной линии не считаются дважды;
- корректировки времени учитываются через `correctedStartAt` / `correctedEndAt`;
- причина и комментарий используются для группировки повторяющихся проблем.

## Метрики заявок

Для заявок считаются:

- время до принятия в работу;
- время до первого действия;
- время выполнения;
- общее время решения;
- просроченные LONG;
- количество передач;
- связь с простоем через `lineStatusEventId`;
- контекстная связь по времени и линии, если явной связи нет.

Явная связь через `lineStatusEventId` считается источником истины. Совпадение по времени не превращается в доказанную причину.

## Центр контроля руководителя

Во вкладке `Статистика / Аудит → Потери` показаны:

- суммарная потеря времени;
- открытые простои;
- срочные открытые заявки;
- просроченные LONG;
- самая проблемная линия;
- средняя и медианная реакция;
- среднее время решения;
- эффект “10 минут в день”;
- линии с потерями;
- реакция отделов;
- крупные простои;
- заявки, влияющие на потери;
- повторяющиеся проблемы;
- качество данных.

UI сделан карточками, чтобы на телефоне не появлялась широкая таблица.

## Качество данных

Stage67 явно показывает предупреждения:

- простои без причины или комментария;
- открытые простои;
- обрезанные/нормализованные интервалы;
- заявки без исполнителя;
- заявки без времени принятия;
- завершённые заявки без подтверждённого времени решения;
- сработавший лимит выборки.

## RBAC и scope

Доступ:

- `ADMIN`;
- `MANAGEMENT`;
- пользователи с `ops.statistics.read` или `ops.overview.read`, если backend разрешает.

Запрещено:

- `WORKER`;
- `CONTRACTOR`;
- `CONTRACTOR_LEAD`;
- guest;
- blocked;
- cross-factory.

Frontend только прячет и структурирует данные. Backend остаётся источником истины.

## Audit/security

Каждый просмотр `/ops/operations/overview` пишет audit action:

- `OPERATIONAL_ANALYTICS_VIEWED`.

Ответы не должны содержать:

- `storagePath`;
- `passwordHash`;
- токены;
- секреты;
- технические пути.

## Ограничения

Stage67 не делает:

- финансовую оценку простоев;
- прогнозирование;
- BI по всем разделам;
- экспорт Excel/PDF;
- автоматический поиск виновных;
- AI/NLP-классификацию причин.
