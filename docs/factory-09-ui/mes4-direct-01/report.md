## Периодический чек-лист: фактическое доказательство и граница UI

Через UI создан двухпунктовый шаблон для Мастеров: ответ Да/Нет **с обязательным фото** и отдельный текстовый ответ. Первоначальный интервал 2 часа не вмещался до окончания текущей смены с 1-часовым grace: первый check завершился, повторное «Начать» вернуло тот же запуск без следующего check. Старый запуск и его история сохранены. Через штатную «Создать копию» создан отдельный учебный 5-минутный шаблон `Учебный периодический контроль №9 — цикл A/B/C`; логика периода в коде не менялась.

В одном новом запуске через браузер **раньше срока** завершены A, B, C с разными текстами, Да/Нет/Да и тремя разными учебными PNG (это тестовые изображения из repo, не физические фотографии оборудования). ## Точный остаток, не скрытый за структурой

1. **Обязательный ручной шаг:** штатная саморегистрация нового профиля требует ввода/подтверждения нового пароля пользователем. Браузерный инструмент не вправе делать этот шаг за него; прямые user/credential записи запрещены. Отдельная вкладка с формой регистрации оставлена пользователю на `127.0.0.1:5173`, указан уникальный учебный телефон `+79900009001`, пароль и подтверждение пусты. До сообщения об успешной регистрации **ни одного** нового учебного пользователя не считаем созданным. Регистрация затем назначение через ADMIN остаются необходимыми для начальника производства, технолога+ОКК, подрядчиков и сменного цикла. Не выдавать отсутствие этих профилей за ручную ошибку владельца.
2. **Security action-time confirmation:** отдельное подтверждение запрошено перед выдачей №9 ровно трём существующим тестовым профилям №4 (КИПиА, электрик, холодильщик). Свежий read-only SQL по известным пользователем окончаниям телефонов подтвердил их отдельные активные UFA №4 и роли `TECH_KIPIA`, `TECH_ELECTRIC`, `TECH_HOLOD`; UFA №9 у этих User нет. Не затрагивать их другие прежние UFA. Пока подтверждения и нового UFA нет, межзаводские уведомления/ссылки/файлы и отзыв/возврат допуска — `NOT_RUN`; №4 UFA не изменён.
3. **TECHNOLOG+ОКК — исправлен только source-путь:** старое копирование прав в `AdminService.permissionCopyPlan/Apply` действительно меняет базовую роль TECHNOLOG→OKK. В существующих `admin.service/controller` и `AdminConfigScreen` добавлен узкий путь для четырёх уже каталогизированных прав `okk.read/manage` и `wash.okk-review.read/manage` как `UserPermissionOverride` **только выбранного завода**. Backend повторно требует ADMIN, совпадение selected factory, активный UFA с ролью TECHNOLOG, действующий завод/пользователя, полный каталог и причину; изменение атомарно аудируется, затем уведомляет об изменении auth. Роль, UFA другого завода и RolePermission не меняются. Изолированный red→green `factory09-authority` проверил отказ MANAGEMENT/чужому заводу/иной роли/пустой причине/неполному каталогу, 4 ALLOW и затем 4 DENY; backend/frontend build PASS, четыре кода прочитаны в `mes`. **Нового технолога пока нет, поэтому выдача через настоящий UI и consumer/notification/archive в live среде остаются NOT_RUN**, а не «исправлено в приёмке». Это единственное продуктовое source-изменение блока.
4. **MANAGEMENT остаётся blocked:** `AdminService.createDepartment/createJobTitle/grantFactoryAccess/updateRoleDepartment` требует ADMIN. Локальное делегирование начальнику №9 должно иметь server-side потолок, UFA/factory/иерархию и запрет межзаводского grant/ADMIN/самоповышения. Простое ослабление этих guard меняло бы правила всех заводов; оно не выполнялось. Выдача ADMIN и глобальных прав не применялась. Позитивный/негативный live цикл под его собственной учёткой пока невозможен: `BLOCKED_ROLE_UI_AND_AUTH`.
5. `NOT_RUN`: учебные явка→назначение→заявка→служба→закрытие→история, запрет двойной линии, реальный 24-часовой сеанс и естественная граница, contractor company-bound и запрет чатов, TECHNOLOG+ОКК операции/фото/архив/уведомления, отдельные учётки и отрицательные factory-проверки, два независимых сеанса, физический телефон, VPS/HTTPS/WSS. Не запускать это на №4 для имитации №9.
6. В обычном checklist-архиве текущие периодические checks появятся после закрытия всего run; пока run ACTIVE. История отдельных завершённых checks должна проверяться через детальный UI под не-fixture исполнителем; SQL доказательство не выдаётся за UI-приёмку. Первоначальный 2-часовой и краткий 5-минутный учебные run остаются ACTIVE до штатного завершения смены; не удалять/закрывать напрямую в БД.

На последнем readback обычное приложение работает: backend Node PID **3860**, `127.0.0.1:3000`; frontend Vite preview Node PID **20532**, `127.0.0.1:5173`; существующая служба PostgreSQL 18 `5432/mes` работает. После нового сообщения инструментарий завершил прежние foreground-сессии 28628/27268; без изменения данных они были запущены снова, `/ready=true`, `/version=MES4-FACTORY9-DIRECT-20260928`, frontend HTTP200. Попытка сделать detached `Start-Process -WindowStyle Hidden` была отклонена политикой инструмента **до создания процесса**; текущие процессы привязаны к терминальным сессиям, поэтому их сохранение после нового сообщения/окончания задачи **не гарантировано**.
