# PRE-VPS-FINISH-01 — единый первый прогон на подтверждённом VPS

**Сейчас не выполнялся.** Сначала получить от владельца точные IP/ОС/resources, SSH user и защищённый способ доступа, независимо подтверждённый host fingerprint, предел sudo, разрешённые каталоги/порты, домен/DNS/TLS, состав пилотных данных и процедуру первого ADMIN. Секреты — только защищённым каналом, не в review/чате. Установка — закрытая техническая, затем отдельное решение о пользовательском пилоте. Не подставлять localhost/старые UUID/учебные пароли вместо этих входов.

Команды ниже принадлежат существующему `setup/zavod-setup.js` (`help`, `prepare`, `bootstrap`, `start`, `check`, `backup`, `update`, `restore-independent`). `REPLACE_*` — обязательные параметры, не готовая конфигурация. Docker Engine/Compose, TLS proxy и сертификаты должны быть установлены и разрешены владельцем сервера; их работоспособность пока `WAIT_VPS`. Не применять `seed.js`.

## Порядок установки и эксплуатации

1. Независимо подтвердить SSH fingerprint/host, ОС/версии, диск/UID/GID, NTP/zone завода, IPv4 и реально включённый IPv6, свободное место, политику портов. Распаковать source ZIP в новый root, сверить все SHA из `RELEASE-MANIFEST.json`. Runtime, DB, uploads, backups, export и logs — разные absolute paths вне source, без symlink/пересечений. Сохранить host/image IDs и их digest.
2. Подготовить доверенный `https://REPLACE_HOST` и `https://REPLACE_HOST/api`, DNS/cert/renewal и внешний proxy по `frontend/nginx.https.example.conf`. Compose DB не публикует host port; backend/frontend привязаны к loopback. Проверить firewall снаружи по IPv4 и включённому IPv6; отсутствие правила в YAML не доказательство закрытости.
3. `node setup/zavod-setup.js prepare --server-address REPLACE_HOST --public-frontend-url https://REPLACE_HOST --public-api-url https://REPLACE_HOST/api --backend-port REPLACE_PRIVATE_BACKEND_PORT --frontend-port REPLACE_PRIVATE_FRONTEND_PORT --db-data-dir REPLACE_DB_DIR --uploads-dir REPLACE_UPLOADS_DIR --backups-dir REPLACE_BACKUPS_DIR --error-reports-dir REPLACE_EXPORT_DIR --logs-dir REPLACE_LOGS_DIR`. `prepare` должен применить 59 миграций, системную основу и остановиться в `FIRST_ADMIN_REQUIRED`: приложение ещё не запущено, поэтому `/ready` пока не требовать. Сверить миграции по факту; не принимать одну конфигурацию за Linux PASS.
4. Первый технический ADMIN — только штатный `node setup/zavod-setup.js bootstrap --factory-name REPLACE_INITIAL_FACTORY --factory-code REPLACE_CODE --admin-phone REPLACE_PHONE --admin-last-name REPLACE_NAME --admin-first-name REPLACE_NAME --credential-file REPLACE_MODE600_FILE`. Файл создан оператором защищённо непосредственно перед действием, не копируется в ZIP. После успешного bootstrap и запуска проверить `/ready`, затем обычный вход/смену личного пароля/новый сеанс; никаких demo seed/общего известного пароля. Не выполнять bootstrap на старой `mes`.
5. `node setup/zavod-setup.js check`; отдельные HTTPS/WSS запросы без ignoreTLS, CORS exact origin, фото >1 МиБ и отрицательный boundary/oversize, SHA скачанного файла, отсутствие публичного URL к storage. Проверить mounts/UID/GID после Compose recreate и серверного reboot, `APP_VERSION` `/version`/UI и фактические image digest. При ошибке остановить допуск, сохранить sanitized logs, не очищать БД.
6. Только после решения владельца о данных: ADMIN экспортирует конфигурацию локальных №4/№9, server UI preview/create и readback local keys/связей. Две реальные будущие камеры №9 создаются UI по требованию. Пилотные люди/операции из `mes` не переносятся. Согласованные новые аккаунты и секреты создаются отдельно. Не путать импорт справочников с restore всей истории.
7. Для регулярного backup: использовать `node setup/zavod-setup.js backup` под отдельным защищённым operator account; проверять exit status, новый complete manifest/TOC/checksums и свободное место. Простой schedule — systemd timer с `OnCalendar=*-*-* 02:00:00`, `Persistent=true`, unit `ExecStart=/usr/bin/node REPLACE_SOURCE_ROOT/setup/zavod-setup.js backup`, `Environment=ZAVOD_SETUP_RUNTIME=REPLACE_PROTECTED_RUNTIME`; проверить владельца/permissions/journal на целевом Linux. Политика хранения: **не менее двух последних полных пар и 30 дней**, срок/частоту согласовать с владельцем. Автоматическое удаление в source не реализовано: просроченные пары удалять только после подтверждённой защищённой второй копии вне VPS и независимого restore; ошибка timer/места видна через systemd failed unit/journal и требует реакции. Не считать это подключённым облаком или проверенным расписанием.
8. Один независимый restore: новая пустая подготовленная цель `prepare --restore-target` с **другими** paths/instance/env/ports, затем `restore-independent --backup REPLACE_BACKUP_IN_TARGET_BACKUPS_DIR --confirm ВОССТАНОВИТЬ_В_НОВУЮ_ЦЕЛЬ`. Проверить DB counts, file bindings/SHA, обычный вход только по согласованной процедуре и original instance unchanged. Не использовать in-place restore на `mes`; не обещать lossless rollback поверх новых операций.
9. Update — только после backup/readback и совместимости схемы: `node setup/zavod-setup.js update --backup REPLACE_VALID_BACKUP_DIR`; новая release/image identity должна отличаться, `/ready` и ожидаемая `/version` совпасть, `updatePending` снят только после READY. При сбое сохранять pending/old image IDs и остановиться на recovery; никакого автоматического DB downgrade. Старой открытой PWA дать завершить черновик и проверить reconnect/checkId/idempotency.
