# VPS-TECH-01 — карта конфигурации и source-only preflight

## Изменение R1 / фактическая граница

[Точный diff/evidence](r1/report.md). `setup/zavod-setup.js` теперь требует оба `publicFrontendUrl=https://<trusted-host>` и `publicApiUrl=https://<same-host>/api` для публичной установки, формирует точный `CORS_ALLOWED_ORIGINS`; приватный HTTP допускается лишь на loopback. `backend/src/main.ts` отказывает production при пустом allowlist. `frontend/nginx.production.conf` маршрутизирует `/api/` и `/ws` к backend в Compose; `frontend/nginx.https.example.conf` — **неактивный** operator TLS template с внешними cert/host/port placeholders. Никакой issuer, сертификат или доверенный browser transport не проверялись.

Backup в existing setup owner останавливает и повторно проверяет backend/frontend своего Compose project перед pg_dump/copy, публикует только проверенный complete pair и возвращает исходно работающие сервисы. Старые архивы без нового consistency marker остаются историческими, но не проходят новый update/independent-restore gate. Источник внешних host-writes и реальная SQL/file согласованность требуют Linux drill. `restore`/web in-place отключены; `prepare --restore-target` и `restore-independent` требуют отдельный пустой target, проверяют source/target identity, paths/ports/config/env/checksums и не копируют source routing/DB secret/JWT. Target `REGISTRATION_FACTORY_CODE` переносится только по явному совпадающему контракту; приложение не стартует автоматически. `update` сверяет schema fingerprint и иной release, сохраняет immutable old image tags/IDs и `updatePending`/`previousRelease`; настоящий rollback остаётся runtime gate. Старые пять source gaps ниже — состояние **до R1**, не текущие незакрытые исходники.

Карта перечисляет **имена** параметров и подтверждённые owner-пути, без значений секретов. Рабочий `backend/.env`, прежние protected runtime/backup и SSH config не читались. Это не работоспособная VPS-конфигурация.

## Подтверждённые source gaps до соответствующего runtime PASS

1. `setup/zavod-setup.js:normalizeConfig/makeEnv` строит `PUBLIC_API_URL` и frontend origin только как `http://<serverAddress>:<port>`; `frontend/nginx.production.conf` обслуживает static HTTP и не является HTTPS/WSS reverse proxy. `CORS_ALLOWED_ORIGINS` не попадает в generated `production.env`; backend `configuredCorsOrigin()` при пустом списке возвращает `true` (разрешает любой Origin для CORS). Перед публикацией нужен выбранный доверенный origin/TLS и адресное изменение/защищённая конфигурация existing setup/proxy owner с source+real HTTPS/WSS регрессией. Это source-confirmed gap, не результат новой live атаки.
2. `createBackup()` последовательно делает `pg_dump`, затем копирует uploads при потенциально работающем backend и только после — config. В коде нет общей write-quiesce/snapshot границы пары DB↔files; `docs/backup-restore.md` лишь рекомендует остановить writes. Нельзя называть такой архив гарантированно согласованным. Перед backup/restore PASS — минимальная граница консистентности в существующем owner и независимый drill на новой цели.
3. `restoreBackup()` работает **in-place**: `dropdb`/`createdb` настроенной DB, затем перенос uploads; в конце копирует **source** `zavod.config.json` и `production.env` из backup в runtime назначения и вызывает `startServices()`. Для independent restore это может перенаправить запуск к source instance/paths. На подтверждённом сервере текущую команду не выполнять на независимой цели до адресного исправления и негативного теста source-isolation. T1 и рабочие данные не использовать.
4. `updateServices()` проверяет full backup и пересобирает images, но не содержит доказанного автоматического rollback к прежнему image/совместимому release. Same-image deploy не закрывает update/rollback gate. Нужны две явно идентифицированные версии и согласованный безопасный путь возврата с SQL-совместимостью.
5. Build release ID вычисляется из native relative path strings + bytes. По текущему списку Windows-host digest `8565dfb365d7043c…`, Linux-path expected `d2749fbc9a95f984…`; не сравнивать их как bytes drift. Итоговый image/release идентификатор фиксируется только на целевом Linux. Это не повод обновлять зависимости или migration.

Ни один source gap не исправлялся вслепую в этом checkpoint; нет подтверждённого target для live regression. Не создавать параллельный proxy/installer/restore. Неблокирующие для приватной C0 проверки пункты TLS и update не объявляются выполненными; backup/independent restore — обязательные технические gates до финальной приёмки.
