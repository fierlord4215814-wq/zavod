# Пласт 10: bounded discovery admin control plane

Дата проверки: 12.08.2026.

## Границы

Проверен существующий admin control plane без создания второго справочника, второй RBAC-системы или параллельного конструктора составов. Бизнес-модули, Prisma schema и миграции не расширялись.

Migration: не нужна. Текущие модели уже хранят заводы, отделы, должности и их иерархию, пользователей и доступы, линии, позиции, шаблоны состава, рабочие зоны, роли, настройки модулей, recovery и аудит.

## Фактические разделы админки

Canonical frontend: `frontend/src/screens/AdminConfigScreen.tsx`.

Найдено 14 реальных разделов:

1. Обзор.
2. Заводы.
3. Пользователи и доступы.
4. Отделы и службы.
5. Должности и роли.
6. Линии и позиции.
7. Позиции на линиях.
8. Шаблоны состава.
9. Повременщики / рабочие зоны.
10. Роли и права.
11. Настройки модулей.
12. Восстановление.
13. Диагностика данных.
14. Аудит действий админки.

Canonical backend: `backend/src/modules/admin/admin.controller.ts` и `backend/src/modules/admin/admin.service.ts`. Производственные линии и шаблоны состава обслуживает существующий `LineService`; право руководителя мастеров определяется `StaffingControlPolicyService` через завод, полномочия и дерево должностей.

## Переиспользованные контуры

- `Factory`, `UserFactoryAccess`, `Department`, `JobTitle` и `AuditLog` — организация, RBAC и аудит.
- `Line`, `LinePosition`, `LineStaffingTemplate` и `LineStaffingTemplateItem` — единый canonical состав линии.
- `Line.defaultStaffingTemplateId` — основной состав, который читают линии, смена и назначения.
- `WorkArea` и `WorkAreaPosition` — существующие повременные рабочие зоны.
- checklist, chat, task и announcement services — реальные consumers созданных в админке справочников.
- существующий recovery endpoint и soft-deactivate flow — штатная очистка тестового integration slice.

## Подтверждённые разрывы

1. `diagnosticRecovery` уже загружался с backend, но не отображался в UI. Из-за этого диагностические soft-deactivated записи нельзя было штатно восстановить через видимую админку. Список и действие восстановления подключены к уже существующему endpoint; новый API не создавался.
2. Management-список объявлений при `activeOnly=false` брал первые 100 записей в порядке приоритета и мог не показать только что созданное обычное объявление. Для административного полного списка применён порядок по дате создания; исходные данные не менялись.
3. Восстановление маршрута frontend могло конкурировать с quick navigation после входа. Устранена гонка, из-за которой E2E открывал не выбранный рабочий экран.
4. Слишком широкое распознавание слова `e2e` могло ошибочно считать обычный пользовательский текст тестовым. Проверка ограничена отдельным marker-токеном.
5. Модальные подтверждения не имели достаточно точных accessible-имён для реального browser flow. Контракт aria-label уточнён без изменения логики.
6. Архивирование группового чата было доступно в backend, но рабочий UI и realtime-обновление нуждались в завершении. Использован существующий chat contour; сообщения и история сохраняются.

Декоративных форм, сохраняющих данные только локально во frontend, после проверки не найдено. Реального отдельного admin-контура custom fields и глобальных уведомлений в текущей v1.0 нет: `NOT_APPLICABLE`, без feature creep.

## Что не трогалось

- Prisma schema и миграции.
- `.env`, uploads, backup/restore.
- реальные рабочие записи и история.
- правила смен, качества, мойки и других модулей вне необходимого чтения canonical справочников.
- физическое удаление записей.
